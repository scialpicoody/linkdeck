# Frontend stack research — LinkDeck v1 in the mygo webview

**Ticket:** #7 · **Date:** 2026-10-24 · **Branch:** `research/frontend-stack`

**Recommendations:**

1. **Styling:** adopt Tailwind CSS v4 (`@tailwindcss/vite`) + hand-ported shadcn-style
   tokens/components. Do **not** adopt the shadcn CLI/React component set — this
   frontend is vanilla TS with no React, and shadcn components are React.
2. **Terminal:** adopt **xterm.js** (`@xterm/xterm` v6.0.0) with the canvas renderer
   default, bounded `scrollback`, and app-level flow control mapped onto mygo
   channels. No blocker; no alternative needed.
3. **Lua editor:** adopt **Monaco** (`monaco-editor` 0.57.0), ESM build, lazy-loaded
   via dynamic `import()` with Vite `?worker` for `editor.worker` only. No blocker:
   Lua is a built-in basic language, and all assets bundle locally (offline-safe).

All claims below were verified against primary sources: the library repos and docs
themselves, the npm registry, and the mygo source at the pinned version
(`github.com/egoist/mygo v0.6.3` in `go.mod`).

## Platform facts (constrain everything below)

- mygo windows render **a web page in the OS webview**: WKWebView on macOS,
  WebKitGTK on Linux, WebView2 on Windows
  (source: `mygo@v0.6.3/README.md`). Only modern evergreen engines are in play on
  macOS/Windows; on Linux the engine is whatever WebKitGTK the distro ships, so
  prefer widely-supported CSS and test on the oldest targeted distro.
- In production the frontend is served from files embedded in the binary at
  `mygo://localhost/`; during `mygo dev` it is the Vite dev server
  (source: `mygo@v0.6.3/frontend.go`, `mygo.config.ts`). Either way it is
  **same-origin over a local scheme** — no CDN is involved or needed, and JS
  workers emitted as separate asset files load fine. (Content-blocker rules are
  opt-in per page — `content_rules.go` — not a default constraint.)
- Frontend ↔ Go is typed IPC: bound-service methods become typed TS functions
  (`Greeter.greet/info` in `src/mygo.ts`, generated by `mygo generate`), Go
  `NewEvent` values become `events.*.on(...)` subscriptions, and `mygo.Channel[T]`
  streams chunked values with **backpressure: `Send` blocks while the page has
  more than 1 MiB of untaken values** (`channel.go`: `const channelWindow = 1 << 20`).
  A fast producer therefore cannot pile memory on the Go side — but the page side
  still needs its own flow control (see xterm below).
- mygo exposes OS theme/accessibility prefs to the page: `runtime().preferences`
  plus `onPreferences` (`index.js`/`index.d.ts`), encoding accent color,
  `reduceMotion`, `reduceTransparency`, `highContrast`, `textScale`
  (`types.d.ts`: `ThemePreferences`). There is **no dark/light field** — color
  scheme must come from CSS (`prefers-color-scheme` / `light-dark()`), which the
  webviews derive from the OS setting.

## 1. shadcn-style components + Tailwind in this Vite setup

### Integration path

- Tailwind v4's Vite path is: `npm install tailwindcss @tailwindcss/vite`, add
  the `tailwindcss()` plugin to `vite.config.ts`, `@import "tailwindcss"` in CSS
  (source: [Install Tailwind CSS with Vite](https://tailwindcss.com/docs/installation/using-vite)).
  Our `vite.config.ts` currently has no plugins, so this is a two-line change
  plus the CSS import. Zero config-file or PostCSS setup.
- The shadcn Vite path is documented for **React + TypeScript** projects: it
  requires `@vitejs/plugin-react`, an `@/*` path alias, and `npx shadcn@latest init`
  (source: [shadcn/ui Vite installation](https://ui.shadcn.com/docs/installation/vite)).
  Components are imported as TSX (`@/components/ui/card`) and are built on
  `@radix-ui/*` primitives — i.e. **shadcn is not a dependency but a
  copy-paste collection of React components**. There is no vanilla-TS/JS track.
- Our frontend is vanilla TS with no framework (`package.json` has no React;
  `src/main.ts` is direct DOM). So "shadcn-style" here must mean one of:
  - **(a, recommended)** port the shadcn *design tokens and class patterns*
    (CSS variables + Tailwind utilities, hand-written DOM components) without the
    CLI/Radix layer; or
  - **(b)** add React + Radix and use the CLI for real. That buys accessibility
    (focus management, ARIA in Radix) at the cost of a framework migration that
    dwarfs the styling question — a separate decision, not part of this ticket.

### Theming with light-dark

- shadcn's theming model is CSS variables (`--background`, `--primary`, …)
  defined under `:root` and overridden under `.dark`, exposed to Tailwind via
  `@theme inline`, with dark mode toggled by a `.dark` class
  (source: [shadcn/ui Theming](https://ui.shadcn.com/docs/theming), which uses
  `@custom-variant dark (&:is(.dark *));`).
- Our codebase already does the equivalent natively: `main.go` passes
  `BackgroundColor: "light-dark(#f6f7f9, #0f1115)"` and `src/style.css` uses
  `color-scheme: light dark` + `@media (prefers-color-scheme: dark)`. The
  webviews track the OS setting, so `prefers-color-scheme` / `light-dark()` work
  with no JS theme provider — simpler than shadcn's class toggle and consistent
  with the native window background (avoids a white-flash/dark-flash mismatch).
- **Caveat (sourced):** shadcn's default token values are `oklch(...)`. oklch
  needs Chrome 111+ / Safari 16.2+ / Firefox 113+ era engines. Fine on macOS
  (WKWebView updates with the OS) and Windows (evergreen WebView2), but an older
  distro WebKitGTK may lack it. If we port the tokens verbatim, keep an sRGB/hex
  fallback row or pin minimum distro versions; alternatively author our tokens
  in hex and keep `light-dark()`/`prefers-color-scheme` for switching.

### Bundle impact

- Tailwind v4 scans sources and emits only used utilities — "zero-runtime"
  (source: Tailwind Vite install doc). Styling cost is a few KB of CSS, no JS.
- A hand-port (option a) adds **no runtime dependency at all**. The real shadcn
  path (option b) would add React + React-DOM + per-component Radix packages +
  `class-variance-authority`/`clsx`/`tailwind-merge` — justified only if we take
  the framework decision, not for styling alone.

### Go interop

None needed beyond what exists: theming is pure CSS (OS-driven, plus mygo's
`preferences()`/`onPreferences` for accent/reduced-motion if we want to honor
them); components call Go through the same `call`/`event` bindings as today.
No mygo API gap.

## 2. Terminal renderer for high-throughput frame streams: xterm.js

**Verdict: adopt `@xterm/xterm` (v6.0.0 current). No alternative evaluation needed —
no webview or memory blocker found.**

### Webview compat

- xterm.js officially supports "the latest versions of Chrome, Edge, Firefox,
  and Safari", works in Electron, and its core has **zero dependencies**
  (source: [xtermjs/xterm.js README](https://github.com/xtermjs/xterm.js)).
  WKWebView, WebView2, and modern WebKitGTK are exactly these engines, so the
  support statement covers all three mygo backends. The default renderer is
  canvas-based (no WebGL required); `@xterm/addon-webgl` is an *optional*
  WebGL2 addon (source: `addons/addon-webgl/README.md`). Recommendation: ship
  the default canvas renderer — one less GPU-context failure mode (the addon
  README itself documents context-loss handling embedders must write) — and only
  evaluate WebGL if profiling shows canvas-bound frames.
- Footprint is small: the published v6.0.0 bundle is **~345 KB ESM
  (`lib/xterm.mjs`) / ~489 KB CJS**, plus sourcemaps, zero dependencies
  (measured from the npm registry file listing for `@xterm/xterm@6.0.0`).
  Tree-shaken through Vite it stays a minor slice of the app.

### Memory behavior under flood

- `Terminal.write()` is non-blocking: it buffers and processes at most ~12 ms of
  input per turn (`WRITE_TIMEOUT_MS = 12`, source:
  [`WriteBuffer.ts` (6.0.0)](https://raw.githubusercontent.com/xtermjs/xterm.js/6.0.0/src/common/input/WriteBuffer.ts)).
  Sustained throughput is documented at roughly **5–35 MB/s** against producers
  that can reach GB/s — so an unthrottled serial-frame stream *will* outrun it
  (source: [Flow Control guide](http://xtermjs.org/docs/guides/flowcontrol)).
- The write buffer has a hardcoded **~50 MB discard watermark** (`DISCARD_WATERMARK`),
  past which `write` **throws and data is lost** — it is a crash parachute, not a
  strategy (same sources). Separately, scrollback history defaults to
  **1000 lines** (`DEFAULT_OPTIONS.scrollback`, source:
  [`OptionsService.ts` (6.0.0)](https://raw.githubusercontent.com/xtermjs/xterm.js/6.0.0/src/common/services/OptionsService.ts))
  and is cap-able (`scrollback: 0` disables), so history memory is bounded by
  configuration, not by input rate.
- The documented answer is caller-side flow control using `write`'s completion
  callback with high/low watermarks (rule of thumb: HIGH ≤ ~500 KB to keep
  keystroke latency snappy), pausing the source in between
  (source: Flow Control guide). Our source is not an OS pty but a Go producer,
  which maps cleanly onto mygo primitives:
  - **Preferred:** stream frames over `mygo.Channel[T]` — `Send` already blocks
    past 1 MiB of untaken values, giving Go-side backpressure for free. On the
    page, gate channel consumption on xterm's write callbacks (only take the
    next chunk when the previous write completes), with a HIGH/LOW watermark to
    avoid per-chunk pause/resume churn, exactly per the guide's advanced pattern.
  - Batch small frames into fewer, larger `write()` calls (per-chunk callbacks
    are the guide's called-out inefficiency; the fast path is `write` without a
    callback for most chunks).
  - Cap `scrollback` (e.g. a few thousand lines for a frame monitor, not
    unlimited) and use `scrollOnUserInput`/viewport pinning so render cost stays
    flat under flood.
- **What not to do:** rely on the 50 MB watermark, or use `writeSync`
  (deprecated, "will lose the current data chunk", per `WriteBuffer.ts`).

### Go interop

xterm.js is input/output agnostic — it renders what the page writes and emits
keystrokes the page forwards. Both directions ride existing mygo IPC:
frames down via `Channel` (backpressured) or typed events (unbackpressured —
prefer channels for streams), keystrokes up via bound-service `call`s. No new
mygo API needed. One design note: channels are parameters of bound methods only
(`channel.go`), so the terminal feed wants a `Shell.tail`-style method taking a
`*mygo.Channel[string]` (the doc comment's own example), not a free-floating
event.

## 3. Monaco for embedded Lua editing

**Verdict: adopt `monaco-editor` (0.57.0 current), lazy-loaded. No blocker.**

### Bundle weight (measured, npm registry, `monaco-editor@0.57.0`)

| Piece | Size (min, uncompressed) | Loaded when |
|---|---|---|
| Core editor chunk (`min/vs/editor-*.js`) | ~2.47 MB | editor opens |
| `editor.main.css` | ~391 KB | editor opens |
| `editor.worker` (needed for all languages) | ~275 KB | editor opens |
| Lua language definition (`min/vs/lua-*.js`) | **~2.1 KB** | Lua model created |
| TS worker | ~7 MB | **never** (Lua doesn't need it) |
| Full `min/` payload | ~25.6 MB | never shipped whole |

The core is the cost (~2.5 MB uncompressed, far less over the wire/gzip — and
here it's local files, so the cost is disk + parse time, not network). Lua
itself is a rounding error, and crucially the multi-MB language workers (TS/CSS/HTML)
are only fetched if those languages are used. For a Lua-only editor the worker
set is just `editor.worker`.

### Lazy-load path (official, Vite-native)

Microsoft's own ESM guide gives the Vite pattern: implement
`self.MonacoEnvironment.getWorker` (not `getWorkerUrl`) returning
`new Worker(...?worker, { type: 'module' })` per label, importing from
`monaco-editor` ESM paths
(source: [Integrating the ESM version — Using Vite](https://raw.githubusercontent.com/microsoft/monaco-editor/main/docs/integrate-esm.md)).
Concretely for us:

1. `const monaco = await import("monaco-editor")` inside the editor-open path
   (dynamic import → Vite code-splits it out of the initial chunk, so the ~2.5 MB
   never touches startup).
2. `MonacoEnvironment.getWorker` mapping only the labels we use to
   `?worker` imports (`editor.worker` for Lua; add `json.worker` etc. only if we
   later edit those languages).
3. `monaco.editor.create(el, { language: "lua", ... })` — Lua is a built-in
   basic language (`esm/vs/languages/definitions/lua/lua.js` ships in the
   package; the 2.1 KB min chunk above is its whole weight). No extra grammar
   package, no TextMate/WASM loading.

### Webview file-access constraints

There are effectively none for our use case:

- Everything above is **bundled local assets** — no CDN, satisfying the offline
  requirement; in production they are served from the embedded `mygo://`
  frontend like any other Vite asset (see platform facts).
- Monaco never touches the filesystem itself: content lives in in-memory models
  (a model without a URI is `inmemory://model/N`; `file:///` URIs are just a
  naming convention for the virtual model space — source: monaco-editor README
  "URIs" section). Persistence is our code: read file bytes in Go, `call` them
  into the page, `setValue`; save via a bound-service `call`. No webview file
  API, drag-and-drop plumbing, or extra mygo surface is required (though
  `onFileDrop` exists if we later want drop-to-open).
- Workers under the custom `mygo://` scheme are the one thing to smoke-test on
  all three OSes during implementation (module workers + custom schemes are the
  historically finicky combination), with the fallback being inlining the
  worker via Vite's `?worker&inline` (blob URL) — a build-flag change, not a
  design change.

> **Build correction (integration, Vite 8/Rolldown):** neither `?worker` nor
> `?worker&inline` resolves AT ALL in this pipeline — static or dynamic
> (build-verified, three attempts). The editor ships with NO worker
> (`MonacoEnvironment.getWorker` unset): Monaco runs on the main thread,
> which is fine for KB-sized Lua scripts. Revisit only if files grow or a
> future Vite version restores `?worker` support.

### Go interop

Same story as xterm: Monaco is a view over strings. Load/save/filename-list via
typed `call`s; live collaboration or external-change notifications via events.
For large files prefer passing content in chunks or via a channel rather than
one giant `call` return. No mygo API gap; the only new Go surface is the
script-store service itself (a later ticket's design).

## Cross-cutting notes

- **No alternative libraries evaluated**, deliberately: xterm.js and Monaco are
  each the de-facto standard (VS Code uses both), both cleared webview compat
  with only configuration-level caveats, and the ticket asks for alternatives
  only if the primary fails.
- **Startup budget:** keep both heavyweights out of the initial chunk —
  xterm.js (~345 KB) can also be dynamically imported with the terminal panel;
  Monaco must be. Initial load stays today's near-zero plus Tailwind CSS bytes.
- **Linux floor:** the one genuine webview risk in the whole stack is old
  WebKitGTK (oklch tokens, module workers). Recommend recording minimum tested
  distro versions when the UI phase starts.
- **A11y hooks exist if needed:** xterm screen-reader mode
  (`screenReaderMode` option); mygo forwards `reduceMotion`/`highContrast`/
  `textScale` prefs. Not v1 scope, but no dead ends.
